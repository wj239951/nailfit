# NailFit 设计说明

## 一句话

规则决定推荐什么，模型决定怎么说；输出是款式库里的真实图片，不做生成式试戴。

## 为什么这样分层

| 层 | 内容 | 放哪 | 为什么 |
|---|---|---|---|
| 标签体系 | 特征枚举、款式属性、权重 | `data/taxonomy.yaml` | 改维度不用改代码 |
| 判断力 | 20 条匹配规则 | `data/rules.yaml` | 可单测、可解释、改一条只影响一条 |
| 记忆 | 款式库（图 + 标签） | `data/styles.*.json` + `static/` | 结构化过滤 + 语义检索 |
| 表达 | 话术风格、输出 JSON 契约 | system prompt | 只有"怎么说"该交给模型 |

**规则不放进 prompt**：prompt 里塞 20 条规则会漏、会曲解，且无法单测；
**规则也不放进向量库**：向量检索是模糊匹配，规则需要精确命中。

## 数据流

```
HandFeatures → RuleEngine.filter_styles()  → 保留可行款式 + 排除理由
             → RuleEngine.score()          → 基础分 + 命中规则加权
             → (可选) SemanticScorer       → 自由描述相似度加分
             → pick_three()                → 三档覆盖 + 色相/色系去重
             → explain()                   → 只生成 reason / caution
             → validate_cards()            → 防编造 + 契约校验
```

## 三个刻意的取舍

1. **甲长必须外部传入**：MediaPipe 关键点没有指甲游离缘，靠它猜甲长是伪科学。
   视觉层应输出"甲长"字段（分割模型或用户选择），本仓库先用手动输入跑通链路。
2. **语义分只是加分项**：默认关闭，Ollama 不可用时静默为 0，主排序永远是规则分。
3. **三选一必须过多样性**：按分数取 top3 会得到三条裸粉，因此按档位取 + 色相去重。

## 与 LLMOps 平台的复用关系

- 复用：模型通道抽象、请求日志、配置加载、API 骨架、前端上传交互
- 替换：检索层（结构化过滤）、编排层（单轮问答 → 多阶段任务）
- 新增：规则引擎、三选一选择器、输出契约校验

## 评测计划

| 指标 | 方法 |
|---|---|
| 合理性 | 30 张真实手照，人工判断"至少 1 条推荐合理"的比例 |
| 多样性 | 三条推荐是否同色系 / 同款式（自动检查） |
| 可解释性 | `matched_rules` 是否真的支持该条推荐 |
| 稳定性 | 同一输入重复 10 次，结果是否一致（规则应完全一致，LLM 只改措辞） |
